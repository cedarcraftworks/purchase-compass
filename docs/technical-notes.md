# 技術解説

Purchase Compass の設計判断を、「何を選んだか」「なぜ選んだか」「何を選ばなかったか」の順にまとめます。判断ごとの詳しい記録は [設計判断の記録（ADR）](adr/README.md)、デモのデータについては [デモ用の購入データについて](sample-data.md) を見てください。

## 1. 全体構成

| 部品 | 役割 | 技術 |
| --- | --- | --- |
| Web | 画面。傾向・おすすめ・気づき・データ取り込み | React, Vite, TypeScript |
| API | 取り込み・保存・分析結果のキャッシュ。DBを持つ唯一の部品 | Hono, zod, postgres.js |
| Analyzer | 分類・集計・傾向の文章化・おすすめ。状態を持たない | FastAPI, pandas, scikit-learn |
| DB | 購入履歴と分析キャッシュ | PostgreSQL |

**DBを触るのはAPIだけ**にしました。分析サービスは「購入データを受け取って結果を返す」だけの部品なので、再起動・台数追加・作り直しをしてもデータ移行が要りません。

**分析結果はデータのバージョンごとにキャッシュ**します。購入を追加・削除するたびにカウンタを1つ増やし、同じバージョンの間は分析をやり直しません。画面を開くたびに重い分析が走ることを防いでいます。

## 2. TypeScriptとPythonを分けた理由

- **画面とAPIはTypeScript**：画面とAPIで型（zodのスキーマ）を共有でき、片方だけ変更して壊れる事故をコンパイル時に防げます。
- **分析はPython**：pandas・scikit-learnなど、データ分析と機械学習の定番ライブラリをそのまま使えます。

**選ばなかった案**

- **全部Python（Djangoなど）**：画面との型共有ができず、画面側の開発体験が落ちます。
- **全部TypeScript**：統計・機械学習のライブラリがPythonほど揃っていません。

**代償として増えたもの**

- 運用する部品が1つ増え、サービス間の通信が失敗する可能性も出ました。
- 対策として、APIは分析サービスの応答を毎回スキーマで検証し、失敗時は壊れたデータを表示せず `502` を返します。
- 2言語間の「食い違い」は、後述の契約テストでCI時に検出します。

## 3. 各技術の選定

| 領域 | 採用 | 理由 | 採用しなかったもの |
| --- | --- | --- | --- |
| 画面 | React + Vite | 実務での採用が多い。ログイン後に使うダッシュボードなのでSPAで十分 | Next.js：SEOもサーバー描画も不要で、サーバー処理はAPIに分けているため過剰 |
| グラフ | 自作のSVG | 棒グラフ2つとヒートマップだけなので、ライブラリを入れるより軽く、見た目も自由 | Chart.js / Recharts：この規模では依存が増えるだけ |
| API | Hono | 軽量で型安全。Web標準の Request/Response に沿うので知識が他でも通用する | Express：型の支援が弱い。NestJS：この規模には重い |
| 入力検証 | zod | スキーマから型を導出でき、画面とAPIで同じ定義を使える | 手書きの検証：型と検証がずれやすい |
| DB接続 | postgres.js | SQLをそのまま書け、プレースホルダで安全。依存がない | ORM（Prismaなど）：集計SQLが主役なので抽象化の利点が小さい |
| 分析API | FastAPI | Pydanticの型定義からAPI仕様書（OpenAPI）が自動生成され、契約テストに使える | Django：管理画面・テンプレートが不要。Flask：型検証と仕様書を自分で組む必要がある |
| DB | PostgreSQL | 集計・制約・トランザクションに強く、実務の標準 | SQLite：複数サービスから同時に使う公開デモに向かない。MongoDB：購入データは表形式で、集計はSQLが素直 |
| テスト | pytest / Node標準のテストランナー | 各言語の標準。Node 22は標準で十分な機能があり、追加の依存が要らない | Jest：TypeScriptとESMの設定に手間がかかる |
| CI/CD | GitHub Actions | コードと同じ場所で動き、公開リポジトリなら無料で使える | 外部のCIサービス：管理する場所が増える |
| 実行環境 | Docker Compose | `docker compose up` の1コマンドで全部品が起動し、面接官の手元でも動く | 手順書のみ：環境の違いで動かないことが多い |

## 4. 分析ロジック

どれも「中学生にも説明できる方法」を選び、結果には必ず理由を添えています。複雑なモデルよりも、**説明できてテストできること**を優先しました。判定の基準値（しきい値）はすべて名前付きの定数にして、テストで境界を確かめています。

### カテゴリ分類（`compass_analyzer/categorize.py`）

1. ユーザーが自分で選んだカテゴリがあればそれを使う
2. キーワード辞書で判定する（例：「コーヒー」→飲料）。速く、結果が予測でき、直すのも単語を足すだけ
3. 辞書で決まらないものだけ、学習済みモデル（文字n-gramのTF-IDF＋ロジスティック回帰）で推定する。自信が低ければ「その他」にする

**文字n-gramを使う理由**：日本語は単語の間にスペースがありません。2〜3文字ずつ区切れば「コーヒ」「ーヒー」のような特徴が取れるため、形態素解析器（MeCabなど）を入れずに済み、サービスを小さく保てます。

**辞書の落とし穴**：「パン」は「パンツ」に含まれてしまうので「食パン」にする、「詰め替え」は日用品だが「シャンプー 詰め替え」は美容なので美容を先に判定する、などをテストで固定しています。

### 傾向の文章化（`trends.py`）

時間帯・曜日・最近の変化・買う場所・中古の割合・1回あたりの金額の6つのルールがあり、**信号が十分に強いときだけ**文章を出します（例：特定の曜日が22%以上のときだけ「◯曜日が多い」と言う）。何でも言うと、大事な傾向が埋もれるためです。

### そろそろ買い時（`habits.py` の `replenishment`）

- 同じ商品を3日以上に分けて3回以上買っていれば、購入間隔の**中央値**を「いつもの周期」とします。
- 平均ではなく中央値なのは、まとめ買いのような外れ値に引っ張られないためです。
- 前回から周期の9割が過ぎたら「買い時」、75%で「もうすぐ」と判定します。

### あなたへのおすすめ（`recommend.py`）

1. **検索キーワードを選ぶ**：購入履歴からキーワードを拾い、最近のもの・金額の大きいものほど重く数えます（安いおにぎり20個より技術書2冊の方が好みを表す、という考え方）。キーワードは1カテゴリにつき1つまでにして、興味の幅を反映させます。
2. **候補を取る**：楽天市場の商品検索APIで候補を取得します。APIキーがない、または失敗した場合は同梱のサンプルカタログで同じ処理をします（一部が落ちても全体は止めない設計）。
3. **並べる**：過去の購入から作った「好みのベクトル」との類似度（コサイン類似度）で並べ、既に持っている物とほぼ同じ商品は除きます。最も似ている過去の購入品を理由として表示します。

**協調フィルタリングを使わなかった理由**：「あなたに似た人はこれも買った」には他の利用者のデータが必要です。このアプリは1人分のデータしか持たない設計なので、商品の文章同士を比べる方法（コンテンツベース）を選びました。

**生成AIを使わなかった理由**：費用がかかる、購入履歴を外部に送ることになる、同じ入力でも結果が変わりテストしにくい、の3点です。

### 定期的な支払い・衝動買い（`habits.py`）

- **定期的な支払い**：同じ支払い先・金額の差5%以内の支払いが、ほぼ一定の間隔（月次なら26〜35日）で3回以上続けば定期課金と判定します。ただし物（コーヒー豆など）を毎月同じ値段で買うのは「買い時」の対象なので、サブスク・デジタル系と不明な支払い先に限っています。
- **衝動買い**：深夜（+30点）、30分以内の連続購入（+25点）、そのカテゴリのいつもの2倍以上の金額（+30点）、初めてのカテゴリ（+15点）を合計し、50点以上を表示します。どの要素で何点入ったかをそのまま理由として見せます。

## 5. データの取り込み

| 店 | 公式の出力 | 取り込み方 |
| --- | --- | --- |
| Amazon | あり（データのリクエスト） | 列名から自動で認識。キャンセルした注文は除外 |
| 楽天 | 見当たらない | 購入履歴の表をコピーして貼り付け、またはCSV |
| メルカリ | 見当たらない | 表の貼り付け、またはCSV |
| 実店舗・カード明細 | — | CSVまたは1件ずつのフォーム |

- 公式の出力がない店は、**列名から「日付・商品名・金額」を推測**し、プレビューで確認・修正してから取り込みます。
- 購入履歴を出力するChrome拡張は非公式のものしかなく、店のログイン情報を扱うため、安全面から使わない設計にしました。
- 日付は「2026/05/03 21:10」「2026年5月3日」「ISO形式」など、金額は「¥1,280」「1,280円」などの書き方を吸収します。存在しない日付（2月31日など）は繰り上げずにエラーにします。
- 同じ店・日時・商品名・金額・数量の購入は同一とみなし、**同じファイルを2回取り込んでも二重に数えません**（一意制約で保証）。
- 取り込みは1つのトランザクションで行い、途中で失敗したら1件も保存しません。

## 6. 品質

### 自動テスト

| 対象 | 件数 | 内容 |
| --- | --- | --- |
| Python | 35 | 分類・傾向・買い時・衝動買い・サブスク・おすすめ・楽天API・HTTP |
| TypeScript（API） | 26 | CSV読み取り・日付と金額の正規化・取り込み・API・キャッシュ・デモモード・契約 |
| TypeScript（画面） | 15 | 画面の描画・公開デモのデータと見本CSVが契約どおりか |
| ブラウザ（E2E） | 7 | 公開デモをChromiumで通しで操作：全タブ、見本の取り込み、スマホ幅、キーボード、ダークモード |

- APIのテストは**本物のPostgreSQL**に対して実行します。重複排除やトランザクションはDBの性質なので、モックでは確かめられないためです。
- 楽天APIはテストで実際には呼ばず、記録した応答を使います。外部サービスの状態でテストが落ちないようにするためです。

### 契約テスト

1. Pythonのテストが、分析サービスの実際の応答とAPI仕様書を `contract/` に書き出します
2. TypeScriptのテストが、それを画面・APIと同じzodスキーマで検証します
3. CIでは毎回1を実行してから2を実行するので、片方の言語だけ項目名を変えると**CIで失敗**します

### CI/CD

- **CI**（プッシュ・プルリクエストごと）：Pythonのlintとテスト → TypeScriptのlint・型チェック・テスト・ビルド → Dockerイメージのビルド
- **CD**（mainでCIが通ったときだけ）：ホスティング先のデプロイを起動します。分析サービス → API → 画面の順で、新しい画面が古いAPIを呼ぶことを防ぎます

## 7. セキュリティとプライバシー

- GitHubと公開デモにはサンプルデータだけを置きます。実データ用の `private-data/` は `.gitignore` 済みです。
- 楽天APIのキーは環境変数とGitHubのSecretsで管理し、コードに書きません。
- 楽天APIに送るのは検索キーワードだけで、購入履歴そのものは外部に出しません。
- 公開デモは**読み取り専用**（`DEMO_MODE`）で、訪問者がデータを変えられません。
- SQLはすべてプレースホルダ経由で、文字列連結はしていません。

## 8. あえてやらなかったこと（今後の課題）

| 項目 | 理由 | 本番で必要になったら |
| --- | --- | --- |
| ログイン・複数ユーザー | 1人分の分析ツールとして範囲を絞った | usersテーブルを足し、全テーブルに user_id を持たせる |
| 分析の非同期化 | 1人分・数千件なら同期で数百ミリ秒 | ジョブキューに載せ、分析サービスだけ台数を増やす |
| レシートのOCR | まず取り込みの土台を固めた | 画像から行を抜き出し、既存の取り込み処理に流す |
| おすすめの精度測定 | 利用者が1人では測れない | クリック率を記録して比較する |
